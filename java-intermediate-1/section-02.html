2. 불변 객체

인프런 김영한 강사님의 "김영한의 실전 자바 - 중급 1편" 강의를 듣고 정리한 학습 노트입니다. 강의 PDF를 그대로 옮긴 것이 아니라, 강의에서 설명한 흐름과 예시를 제 나름대로 재구성했습니다.

기본형과 참조형의 공유

  • 기본형은 값을 복사해서 대입하므로 변수끼리 절대 공유되지 않는다 — int b = a; 후 b를 바꿔도 a는 그대로.
  • 참조형은 참조값을 복사해서 대입하므로, 여러 변수가 같은 인스턴스를 가리킬 수 있다 — Address b = a; 후 b의 값을 바꾸면 a도 같이 바뀐다.
  • 둘 다 "값을 복사해서 대입한다"는 같은 원칙을 따르는데, 참조형은 그 값이 참조값이라서 결과적으로 인스턴스를 공유하게 되는 것.

공유 참조와 사이드 이펙트

  • 사이드 이펙트: b만 바꾸려 했는데 같은 인스턴스를 참조하는 a까지 같이 바뀌는 현상 — 의도한 작업 밖에서 예상 못한 부수 효과가 생기는 것.
  • 근본 원인은 공유 참조 자체다. 여러 변수가 하나의 객체를 참조하면 한쪽 변경이 다른 쪽에 그대로 영향을 준다.
  • 문제는 자바 문법상 공유 참조 자체를 강제로 막을 방법이 없다는 것 — 실수로 발생하기 쉽고, 복잡한 코드/여러 메서드 호출 속에서는 원인 찾기가 특히 어려워진다.
  • → 근본적인 해결책은 공유를 막는 게 아니라, 공유된 객체의 값 자체를 못 바꾸게 만드는 것.

불변 객체 도입

  • 불변 객체(Immutable Object): 생성된 후 내부 값(필드)이 절대 바뀌지 않는 객체.
  • 구현 방법: 필드를 final로 선언하고, 값을 바꾸는 메서드(setValue 등)를 아예 만들지 않는다.
  • 값을 바꾸는 메서드가 없으므로 공유 참조가 있어도 사이드 이펙트가 원천적으로 발생하지 않는다.
  • 가변 객체(값 변경 가능)와 불변 객체(값 변경 불가)는 상황에 따라 선택 — 값을 바꿔야 하는 경우가 많으면 가변이 일반적이고, 값이 바뀌면 안 되는 특별한 경우에 불변을 쓴다.
class ImmutableAddress {
    private final String value;

    public ImmutableAddress(String value) {
        this.value = value;
    }

    public String getValue() {
        return value;
    }
    // setValue() 없음 — 값을 바꿀 방법 자체가 없다
}

불변 객체 적용 예제

  • MemberV1이 가변 Address를 갖는 경우: 회원 B의 주소를 바꾸려고 memberB.getAddress().setValue("부산")을 호출하면, 같은 Address를 공유하는 회원 A의 주소까지 "부산"으로 바뀐다.
  • MemberV2가 ImmutableAddress를 갖는 경우: setValue가 아예 없으므로 값을 바꾸려는 시도 자체가 컴파일 오류가 된다.
  • → 회원 B의 주소를 바꾸려면 새 ImmutableAddress 인스턴스를 만들어서 memberB.setAddress(new ImmutableAddress("부산"))처럼 통째로 교체해야 한다. 이 경우 회원 A는 기존 주소를 그대로 유지한다.

불변 객체의 값 변경

  • 불변 객체도 "값을 더한 결과"가 필요한 경우가 있다 — 이때는 자기 자신을 바꾸는 대신 새 객체를 만들어서 반환한다.
class ImmutableObj {
    private final int value;

    public ImmutableObj(int value) {
        this.value = value;
    }

    public int getValue() {
        return value;
    }

    public ImmutableObj add(int addValue) {
        return new ImmutableObj(this.value + addValue); // 새 객체를 만들어 반환
    }
}
  • 중요한 함정: obj1.add(20)만 호출하고 반환값을 받지 않으면 새로 만든 객체는 그냥 버려진다(GC 대상) — obj1은 여전히 원래 값 그대로다.
  • 제대로 쓰려면 ImmutableObj obj2 = obj1.add(20);처럼 반드시 반환값을 받아서 써야 한다.
  • 필드가 final이고 setter가 없으면 불변 클래스라고 판단할 수 있다. 그런 클래스의 "값 변경" 메서드를 보면 "아, 새 객체를 반환하겠구나"라고 바로 인지하는 게 중요하다.

정리

  • 기본형은 값을 공유하지 않지만, 참조형은 참조값을 복사하므로 인스턴스를 공유할 수 있다.
  • 공유 참조 자체는 막을 수 없다 — Side Effect는 "공유"가 아니라 "공유된 값의 변경"에서 생긴다.
  • 불변 객체는 값 변경을 원천 차단해서 Side Effect를 근본적으로 없앤다 (final 필드 + setter 없음).
  • String, Integer, LocalDate 등 자바의 핵심 클래스 다수가 불변으로 설계되어 있다.
  • 불변 객체에서 "값 변경"은 곧 "새 객체 생성 + 반환"을 의미하며, 호출한 쪽은 반환값을 반드시 받아야 한다.
  • 불변 객체는 값이 바뀔 때마다 새 객체를 생성하므로 가변 객체보다 성능이 불리할 수 있다 — 그래도 캐시/멀티스레드 안전성 등 다른 이유로도 불변 설계를 택하는 경우가 많다.
