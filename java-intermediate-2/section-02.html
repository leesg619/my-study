2. 제네릭 - Generic 2

인프런 김영한 강사님의 "김영한의 실전 자바 - 중급 2편" 강의를 듣고 정리한 학습 노트입니다. 강의 PDF를 그대로 옮긴 것이 아니라, 강의에서 설명한 흐름과 예시를 제 나름대로 재구성했습니다.

타입 매개변수 제한 — 동물병원 예제로 단계별로

요구사항: 개 병원은 개만, 고양이 병원은 고양이만 받는다. 병원은 진찰(checkup() — 이름·크기 출력, sound() 호출)과 큰 동물 고르기(bigger())를 제공한다.

시도 1 — 타입별 병원 클래스

  • DogHospital, CatHospital을 따로 만든다.
  • 개 병원에 고양이를 넣으면 컴파일 오류 → 타입 안전 ○.
  • 대신 타입만 다른 클래스가 복사된다 → 코드 재사용 ✕.

시도 2 — 다형성 (Animal로 받기)

  • AnimalHospitalV1의 필드와 매개변수를 부모 타입 Animal로 두면 클래스 하나로 끝난다. Animal에 있는 getName(), getSize(), sound()도 호출할 수 있다 → 코드 재사용 ○.
  • 대신 개 병원으로 쓰려던 객체에 고양이가 들어가도 막을 수 없고, bigger()가 Animal을 돌려주므로 Dog로 다운캐스팅해야 한다 → 잘못 넣으면 ClassCastException. 타입 안전 ✕.

시도 3 — 제네릭 도입, 그런데 컴파일이 안 된다

public class AnimalHospitalV2<T> {
    private T animal;

    public void checkup() {
        // animal.getName();   // 컴파일 오류
        // animal.sound();     // 컴파일 오류
    }
}

new AnimalHospitalV2<Integer>(); // 동물과 무관해도 막을 수 없다
  • 문제 1: 클래스를 정의하는 시점에 컴파일러는 T에 무엇이 들어올지 모른다. 뭐든 올 수 있으니 T는 Object로 간주되고, Object의 기능(toString(), equals() 등)만 쓸 수 있다.
  • 문제 2: 타입 인자로 Integer, Object처럼 동물과 상관없는 타입도 들어온다.
  • → 들어올 수 있는 타입의 범위를 좁혀야 한다.

해결 — T extends Animal

public class AnimalHospitalV3<T extends Animal> {
    private T animal;

    public void set(T animal) { this.animal = animal; }

    public void checkup() {
        System.out.println("동물 이름: " + animal.getName()); // 이제 호출 가능
        animal.sound();
    }

    public T bigger(T target) {
        return animal.getSize() > target.getSize() ? animal : target;
    }
}

AnimalHospitalV3<Dog> dogHospital = new AnimalHospitalV3<>();
// dogHospital.set(new Cat("냐옹이", 300));        // 컴파일 오류
// new AnimalHospitalV3<Integer>();               // 컴파일 오류
Dog bigger = dogHospital.bigger(new Dog("멍멍이2", 200)); // 캐스팅 불필요
  • T extends Animal: T에는 Animal과 그 자식만 올 수 있다. 이때 Animal을 상한(upper bound)이라 부른다.
  • 컴파일러가 "적어도 Animal이다"라고 보장받으므로 Animal의 기능을 T에 호출할 수 있다. 실제 호출은 다형성대로 Dog의 오버라이딩된 sound()가 실행된다.
  • 앞의 문제가 전부 사라진다: 잘못된 동물 전달 ✕, 다운캐스팅 ✕, 무관한 타입 ✕, Object 기능만 사용 ✕ → 재사용과 타입 안전을 함께 확보.

제네릭 메서드

제네릭 타입과는 별개의 기능이다. 클래스 전체가 아니라 특정 메서드 하나에만 제네릭을 건다.

public class GenericMethod {
    public static <T> T genericMethod(T t) {
        return t;
    }

    public static <T extends Number> T numberMethod(T t) {
        return t;
    }
}

Integer result = GenericMethod.<Integer>genericMethod(10); // 타입 인자 명시
Integer inferred = GenericMethod.genericMethod(10);         // 인자 타입으로 추론 — 보통 이렇게 쓴다
// GenericMethod.numberMethod("Hello");                     // 컴파일 오류
  • 반환 타입 앞에 <T>를 선언한다. 이 T는 그 메서드 안에서만 유효하다.
  • 호출할 때 메서드 이름 앞에 타입 인자를 전달하지만, 컴파일러가 인자 타입을 보고 추론해 주므로 대부분 생략한다. 생략했을 뿐, 타입 인자가 정해지는 건 그대로다.
  • 메서드에도 extends로 상한을 걸 수 있다.
제네릭 타입제네릭 메서드
선언 위치클래스·인터페이스 이름 옆메서드 반환 타입 앞
타입 결정 시점객체 생성 시점메서드 호출 시점
static 메서드타입 매개변수 사용 불가사용 가능
  • 제네릭 타입의 T는 인스턴스를 만들 때 결정되는데, static 메서드는 클래스 단위로 동작한다 → static에서는 쓸 수 없고, 필요하면 제네릭 메서드로 선언한다. 인스턴스 메서드도 제네릭 메서드가 될 수 있다.

활용과 우선순위

public class AnimalMethod {
    public static <T extends Animal> void checkup(T t) { ... }

    public static <T extends Animal> T getBigger(T t1, T t2) {
        return t1.getSize() > t2.getSize() ? t1 : t2;
    }
}
  • 앞의 병원 기능을 객체 생성 없이 메서드만으로 호출할 수 있다.
  • 클래스의 T와 메서드의 T가 이름이 같으면 메서드의 T가 우선한다 — 프로그래밍에서는 더 가깝고 구체적인 쪽이 이긴다.
    • 이때 메서드의 T에 상한이 없으면 클래스의 T extends Animal과 상관없이 Object 기능만 쓸 수 있다.
    • 헷갈리기만 하니 이름을 다르게 짓는 게 답이다 (T, Z).

와일드카드

와일드카드(?)는 여러 타입이 들어올 수 있다는 뜻의 특수문자다. 핵심: 제네릭 타입이나 제네릭 메서드를 선언하는 게 아니라, 이미 만들어진 제네릭 타입을 활용할 때 쓴다.

// 제네릭 메서드 — 호출할 때마다 T를 결정하는 과정이 있다
static <T> void printGenericV1(Box<T> box) { ... }

// 와일드카드 — 그냥 일반 메서드에 Box 매개변수가 있는 것
static void printWildcardV1(Box<?> box) { ... }

static void printWildcardV2(Box<? extends Animal> box) {
    Animal animal = box.get(); // 상한 타입으로 꺼낸다
}
  • 비제한 와일드카드 Box<?>: 어떤 Box든 받는다. ? extends Object와 같아서 꺼내면 Object다.
  • 상한 와일드카드 Box<? extends Animal>: Box<Dog>, Box<Cat>은 받고 Box<Object>는 못 받는다. 꺼내면 상한인 Animal이다.
  • 제네릭 메서드와 달리 타입을 결정하는 과정 없이 매개변수만 하나 받는 단순한 구조다 → 제네릭 타입·메서드를 정의할 필요가 없으면 와일드카드를 쓰는 것을 권장.

와일드카드로 안 되는 경우 — 전달한 타입을 그대로 돌려줘야 할 때

static <T extends Animal> T printAndReturnGeneric(Box<T> box) {
    return box.get();
}

static Animal printAndReturnWildcard(Box<? extends Animal> box) {
    return box.get();
}

Dog dog = printAndReturnGeneric(dogBox);        // T = Dog이므로 Dog 반환
Animal animal = printAndReturnWildcard(dogBox); // Animal로만 받을 수 있다
  • 제네릭 메서드는 T가 결정되면 반환 타입까지 함께 바뀐다. 와일드카드는 들어오는 값을 쓰기만 하고 타입을 바꿔 주지 않는다.
  • → 호출 시점에 타입을 결정해야 하면 제네릭 타입이나 제네릭 메서드를, 그렇지 않으면 와일드카드를 쓴다.

하한 와일드카드

  • Box<? super Animal>: Animal과 그 상위 타입만 받는다. Box<Object>, Box<Animal> ○ / Box<Dog>, Box<Cat> ✕.
  • 하한은 와일드카드에서만 쓸 수 있다. 타입 매개변수를 선언할 때 <T super Animal>처럼 쓸 수는 없다.

타입 이레이저

  • 이레이저(eraser) = 지우개. 제네릭은 컴파일 시점에만 존재하고, 컴파일이 끝나면 타입 정보가 지워진다. .java에는 타입 매개변수가 있지만 .class에는 없다.
// 컴파일 전                       // 컴파일 후 (개념적으로)
class Box<T> { T value; }          class Box { Object value; }
Integer i = box.get();             Integer i = (Integer) box.get();

class Hospital<T extends Animal>   class Hospital { Animal animal; ... }
  • 컴파일러는 먼저 T를 타입 인자로 이해해 타입을 검사한 뒤 제네릭 정보를 지운다.
  • 상한이 없는 T는 Object로, T extends Animal은 상한인 Animal로 바뀐다. 상한이 남으니 Animal의 메서드 호출에는 문제가 없다.
  • 값을 꺼내는 곳에는 컴파일러가 다운캐스팅 코드를 자동으로 넣는다. 이미 컴파일 단계에서 타입을 검증했으므로 이 캐스팅은 안전하다.
  • 왜 이렇게 했나? 제네릭이 없던 기존 자바 코드와의 하위 호환을 지키기 위해서다. 컴파일러가 고생하고, 실행되는 코드는 옛날과 똑같이 맞춘다.

이레이저의 한계 — 런타임에 쓸 수 없는 것

class EraserBox<T> {
    public boolean instanceCheck(Object param) {
        return param instanceof T; // 컴파일 오류
    }
    public T create() {
        return new T();            // 컴파일 오류
    }
}
  • 런타임의 T는 Object일 뿐이다. instanceof T는 항상 Object와 비교하는 꼴이 되고, new T()는 항상 new Object()가 되어 버린다 → 자바가 둘 다 막아 둔다.

정리

  • 타입 매개변수 제한: 범위를 좁혀 무관한 타입을 막고, 상한 타입의 기능을 쓸 수 있게 한다.
  • 제네릭 메서드: 메서드 호출 시점에 타입을 결정한다. 와일드카드: 이미 정해진 제네릭 타입을 받아서 활용하는 단순한 도구.
  • 타입 이레이저: 런타임에는 제네릭 정보가 없다 → instanceof T, new T() 불가.
  • 실무에서 제네릭을 직접 깊게 설계할 일은 많지 않다. 라이브러리의 제네릭 코드를 읽고 이해할 수 있으면 충분하고, 공변·반공변 같은 내용은 필요해질 때 공부해도 된다. 나머지는 컬렉션 프레임워크를 쓰면서 자연스럽게 익힌다.
