10. 다형성1

인프런 김영한 강사님의 "김영한의 실전 자바 - 기본편" 강의를 듣고 정리한 학습 노트입니다. 강의 PDF를 그대로 옮긴 것이 아니라, 강의에서 설명한 흐름과 예시를 제 나름대로 재구성했습니다.

다형성이란

  • 다형성(polymorphism)은 "다양한 형태" — 프로그래밍에서는 한 객체가 여러 타입으로 취급될 수 있는 능력을 뜻한다. "객체지향 프로그래밍의 꽃"이라 불릴 만큼 중요하지만 처음엔 실감이 안 나는 개념이다.
  • 다형성을 이해하려면 두 가지 퍼즐 조각이 필요하다 — 다형적 참조와 메서드 오버라이딩. 이번 섹션은 이 두 조각을 각각 이해하는 데 집중한다.

다형적 참조 — 부모는 자식을 담을 수 있다

  • Parent p = new Parent();, Child c = new Child();는 각자 자기 타입을 참조하는 당연한 경우다.
  • 핵심은 Parent p = new Child(); — 부모 타입의 변수가 자식 타입의 인스턴스를 참조할 수 있다는 것. "부모는 마음이 넓어서 자식을 담을 수 있다"는 비유로 기억하면 된다.
  • 반대는 성립하지 않는다 — Child c = new Parent();는 컴파일 오류. "자식은 속이 좁아서 부모를 담을 수 없다."
  • 단, Parent p = new Child();로 참조하면 p.childMethod()처럼 자식만의 메서드는 호출할 수 없다 — p는 Parent 타입이므로 Parent가 아는 멤버만 호출 가능하다(섹션 9의 "호출 타입 기준 탐색" 규칙 그대로).

캐스팅 — 다운캐스팅과 업캐스팅

  • 부모 타입 변수로 자식 메서드를 쓰고 싶다면 다운캐스팅: Child child = (Child) parent;처럼 명시적으로 타입을 낮춘다. 자바가 "위험할 수 있다"고 경고하지만, 개발자가 "내가 책임진다"는 의미로 명시하는 것.
  • 변수 선언 없이 그 자리에서 바로 ((Child) poly).childMethod()처럼 일시적 다운캐스팅도 가능하다 — 연산자 우선순위 때문에 괄호가 필요하다.
  • 중요한 점: 캐스팅은 변수 자체의 타입을 바꾸는 게 아니다. 변수(poly)가 들고 있는 참조값을 읽어와서 잠깐 다른 타입으로 취급할 뿐 — 원래 변수의 타입은 그대로 Parent다. 자바에서 변수는 "대입" 외에는 자기 자신이 바뀌는 일이 없다는 원칙이 여기서도 적용된다.
  • 반대 방향인 업캐스팅(자식 → 부모, Parent p = child;)은 항상 안전하기 때문에 캐스팅 표시를 생략해도 자바가 자동으로 처리해준다 — "부모가 자식을 담는 건 자연스러운 흐름"이라 컴파일러가 굳이 강제로 명시하게 하지 않는 것.

다운캐스팅의 위험 — ClassCastException

  • 객체를 new할 때 메모리에는 그 타입과 그 부모 타입들만 생성된다 — 자식 타입은 생성되지 않는다. 예를 들어 new Parent()로 만든 객체 안에는 애초에 Child 부분이 존재하지 않는다.
  • 그래서 Parent p = new Parent();를 (Child) p로 다운캐스팅하면, 메모리에 있지도 않은 Child 부분을 찾으려다 ClassCastException(런타임 예외)이 발생한다.
  • 업캐스팅은 "객체를 만들 때 이미 부모까지 다 함께 생성되므로" 항상 안전하지만, 다운캐스팅은 "그 자식 부분이 실제로 존재하는지"를 실행 시점에야 확인할 수 있어 근본적으로 위험하다.
  • 컴파일 오류는 실행 전에 IDE가 잡아주지만, ClassCastException 같은 런타임 오류는 프로그램이 실제로 그 코드를 지나갈 때만 터진다 — 사용자가 쓰다가 마주칠 수 있다는 점에서 훨씬 위험하고 고치기도 번거롭다.

instanceof — 안전하게 확인하고 다운캐스팅

  • parent instanceof Child는 "parent 변수가 실제로 참조하는 인스턴스가 Child 타입에 대입 가능한가"를 boolean으로 알려준다. 이해하는 팁: 오른쪽 타입에 왼쪽 인스턴스가 들어갈 수 있는지 대입해본다고 생각하면 된다 — 부모가 자식을 담을 수 있으니 Parent 변수(실제로는 Child) instanceof Child는 true.
  • 다운캐스팅 전에 항상 instanceof로 먼저 확인하는 것이 안전한 패턴이다.
  • 자바 16부터는 패턴 매칭으로 검사와 캐스팅·변수 선언을 한 번에 처리할 수 있다 — if (parent instanceof Child child) { child.childMethod(); }처럼 true인 블록 안에서 바로 child 변수를 다운캐스팅된 상태로 쓸 수 있다.
void callParent(Parent parent) {
    if (parent instanceof Child child) { // 검사 + 캐스팅 + 변수 선언 한 번에
        child.childMethod();
    }
}

다형성과 메서드 오버라이딩의 결합

  • 필드(멤버 변수)는 오버라이딩되지 않는다 — Parent poly = new Child();에서 poly.value는 언제나 Parent가 가진 value를 가리킨다(호출 타입 기준으로 찾기 때문).
  • 반면 메서드는 오버라이딩된 쪽이 항상 우선한다 — 같은 poly.method() 호출이라도, Child가 method()를 오버라이딩했다면 실제 생성된 인스턴스가 Child이므로 Child의 오버라이딩된 메서드가 실행된다. poly의 선언 타입이 Parent인 것과는 무관하다.
  • 정리하면: 필드는 "참조 변수의 타입"을 따르고, 메서드는 "실제 인스턴스에서 오버라이딩된 것"을 따른다 — 이 비대칭이 다형성의 핵심 동작 원리다. 더 하위에서 오버라이딩된 메서드가 있다면 그게 최우선이다.
  • 이 두 조각(다형적 참조 + 메서드 오버라이딩)이 만나야 "부모 타입 변수 하나로 다양한 자식들의 서로 다른 동작을 실행시킨다"는 다형성의 진짜 힘이 나온다 — 다음 섹션(다형성2)에서 이 조합을 실전 활용으로 이어간다.
class Parent { void method() { System.out.println("parent"); } }
class Child extends Parent {
    @Override
    void method() { System.out.println("child"); }
}

Parent poly = new Child();
poly.method(); // "child" — 오버라이딩된 쪽이 우선

정리

  • 다형적 참조: 부모 타입 변수는 자식 인스턴스를 담을 수 있지만, 그 변수로는 부모가 아는 멤버만 직접 호출 가능하다.
  • 업캐스팅은 안전해서 생략 가능, 다운캐스팅은 위험해서 명시가 필수 — 위험한 이유는 객체 생성 시 자식 부분이 아예 메모리에 없을 수 있기 때문(ClassCastException).
  • instanceof(자바 16+ 패턴 매칭 포함)로 미리 확인하고 다운캐스팅하는 것이 안전한 습관이다.
  • 필드는 참조 타입 기준, 메서드는 실제 인스턴스의 오버라이딩 기준 — 이 차이가 다형성이 실전에서 힘을 발휘하는 지점이다.
