김영한의 실전 자바 - 기본편

9. 상속

인프런 김영한 강사님의 "김영한의 실전 자바 - 기본편" 강의를 듣고 정리한 학습 노트입니다. 강의 PDF를 그대로 옮긴 것이 아니라, 강의에서 설명한 흐름과 예시를 제 나름대로 재구성했습니다.

상속이 필요한 이유 — 전기차와 휘발유차

  • ElectricCar는 move()·charge(), GasCar는 move()·fillUp()을 가진다. 둘 다 "자동차"라는 더 큰 개념에 속하고, move()라는 공통 기능은 완전히 겹친다 — 반면 충전 방식은 다르다.
  • 이렇게 공통점과 차이점이 함께 있는 클래스들이 있을 때, 공통 부분을 뽑아 "부모" 클래스(Car)로 만들고 각자의 차이점만 자식 클래스에 남기는 것이 상속의 출발점이다.

상속 관계 — extends

  • class ElectricCar extends Car처럼 extends로 부모를 명시하면, Car의 필드·메서드를 그대로 물려받는다. 자식 클래스는 자기만의 메서드(charge())를 추가로 가질 수 있다.
  • 상속 구조도의 화살표는 자식 → 부모 방향이다 — "내가 상대를 안다"는 뜻이라, extends로 부모를 명시한 자식만 부모를 알고, 부모는 자식의 존재를 전혀 모른다.
  • 자바는 클래스의 다중 상속을 지원하지 않는다 — 여러 부모를 동시에 상속하면 같은 이름의 메서드가 부모마다 다르게 정의됐을 때 어느 쪽을 호출해야 할지 모호해지는 다이아몬드 문제가 생기기 때문이다. (다중 상속 대신 인터페이스의 다중 구현은 가능 — 다형성 섹션에서 다룬다.)
class Car {
    void move() { System.out.println("자동차, 이동"); }
}
class ElectricCar extends Car {
    void charge() { System.out.println("충전"); }
}

상속과 메모리 구조

  • 상속은 단순히 "부모 필드·메서드를 물려받는다"는 것 이상이다 — new ElectricCar()를 하면 메모리 안에 자식과 부모가 동시에 생긴다(하나의 인스턴스 안에 Car 영역과 ElectricCar 영역이 함께 존재).
  • 메서드를 호출하면, 호출에 쓰인 변수의 타입부터 메서드를 찾기 시작한다. electricCar.charge()는 ElectricCar에서 바로 찾아 호출되고, electricCar.move()는 ElectricCar에 없으므로 부모(Car)로 올라가 찾는다. 최상위까지 올라가도 없으면 컴파일 오류.
  • 이 "타입 기준으로 찾다가 없으면 부모로 올라간다"는 탐색 규칙이 뒤에 나올 다형성을 이해하는 토대가 된다.

상속과 기능 추가 — "확장"

  • 모든 차종에 공통으로 필요한 openDoor()를 부모 Car에 한 번만 추가하면, ElectricCar·GasCar 등 모든 자식이 코드 수정 없이 자동으로 그 기능을 갖게 된다.
  • 새 차종(HydrogenCar)을 추가할 때도 Car를 상속하면 move()·openDoor()는 공짜로 얻고, 수소차만의 고유 기능(fillHydrogen())만 새로 작성하면 된다.
  • extends가 "확장"이라는 단어 그대로, 상속은 기존 개념 위에 새로운 기능을 얹어 더 구체적인 개념으로 넓혀가는 과정이다.

메서드 오버라이딩

  • 부모의 기능이 마음에 안 들 때, 자식 클래스에서 같은 시그니처의 메서드를 다시 정의해 덮어쓸 수 있다 — 이것이 오버라이딩. 매개변수만 다르게 여러 메서드를 만드는 오버로딩과는 완전히 다른 개념이니 혼동하지 말 것.
  • @Override 애노테이션을 붙이는 습관이 중요하다 — 메서드 이름을 잘못 적는 등 실수로 오버라이딩이 안 됐을 때, @Override가 있으면 컴파일러가 즉시 오류로 잡아준다. 없으면 그냥 새로운 메서드가 하나 추가된 것으로 조용히 넘어가 버그가 숨는다.
  • 오버라이딩 조건: 메서드 이름·매개변수(타입/순서/개수)·반환 타입이 같아야 하고, 접근 제어자는 부모보다 더 좁아질 수 없다(넓히는 건 가능). 예외도 부모보다 더 많이 선언할 수 없다.
  • 오버라이딩이 불가능한 경우: static(클래스 소속이라 인스턴스 다형성과 무관), final(애초에 재정의 금지가 목적), private(자식이 접근조차 못 함), 생성자(이름이 클래스명이라 상속 개념 자체가 적용 안 됨).
  • 메서드 호출 시에도 앞서 배운 "호출 타입에서 먼저 찾는다" 원칙이 그대로 적용된다 — 자식에 오버라이딩된 메서드가 있으면 부모까지 갈 필요 없이 거기서 멈춘다.
class ElectricCar extends Car {
    @Override
    void move() {
        System.out.println("전기차, 빠르게 이동"); // 부모의 move()를 덮어씀
    }
}

상속과 접근 제어자

  • UML 표기로 +는 public, #는 protected, ~는 default, -는 private을 뜻한다.
  • 부모·자식이 다른 패키지에 있을 때가 접근 제어자의 진짜 시험대다 — public·protected 멤버는 자식이 접근할 수 있지만, default·private 멤버는 접근할 수 없다(protected가 "같은 패키지 + 상속 관계"까지 열어준다는 정의가 여기서 실제로 확인된다).
  • 앞서 배운 메모리 구조(부모·자식 영역이 객체 내부에서 분리되어 존재)가 여기서도 그대로 적용된다 — 영역이 나뉘어 있기 때문에 그 경계를 넘는 접근은 접근 제어자의 통제를 받는다.

super — 부모를 명시적으로 가리키기

  • this가 "나 자신"이듯, super는 "내 부모"를 가리킨다. 자식과 부모에 이름이 같은 필드나 메서드가 있을 때, 아무 표시 없이 쓰면 자식 것이 우선 적용된다 — 부모 것을 쓰고 싶다면 super.value, super.hello()처럼 명시해야 한다.
  • this는 생략 가능하지만(가까운 스코프부터 자동으로 찾아줌), super는 생략하면 자동으로 부모를 찾아주는 게 아니라 아예 자식의 멤버로 해석돼버리므로 부모 것이 필요하면 반드시 명시해야 한다.

super — 생성자 호출

  • 상속 관계에서 인스턴스를 만들면 부모와 자식이 메모리에 함께 생긴다고 했다 — 그 말은 부모의 생성자도 반드시 호출되어야 한다는 뜻이다. 자식 생성자는 자기 로직을 실행하기 전에 반드시 부모 생성자를 먼저 호출해야 하며, 이를 위한 게 super(...)다.
  • 부모에 매개변수 없는 기본 생성자만 있다면 super() 호출은 생략해도 된다 — 자바 컴파일러가 자식 생성자 첫 줄에 자동으로 super()를 끼워 넣어주기 때문. 반대로 부모에 매개변수 있는 생성자만 있고 기본 생성자가 없다면, 자식은 반드시 super(값)을 명시적으로 호출해야 한다.
  • 생성자 실행 순서는 항상 최상위 부모부터 시작해서 자식 쪽으로 내려온다 — 자식이 부모의 데이터를 활용할 수 있으려면 부모가 먼저 초기화되어 있어야 하기 때문에 합리적인 순서다.
  • this(...)로 같은 클래스의 다른 생성자를 호출하더라도, 그 체인의 끝에서는 결국 super()가 반드시 한 번은 호출되어야 한다 — 생성자의 첫 줄은 언제나 this(...) 또는 super(...) 둘 중 하나(혹은 생략된 암묵적 super())다.
class ClassB extends ClassA {
    ClassB(int value) {
        super(value); // 부모 생성자 먼저 호출 — 반드시 첫 줄
        // 이후 자식 초기화 로직
    }
}

final과 상속

  • final class는 더 이상 상속할 수 없다(다른 클래스가 extends 할 수 없음). final method는 오버라이딩할 수 없다 — "더는 확장/재정의를 허용하지 않겠다"는 명시적 선언이다.

정리

  • 상속은 공통 기능을 부모로 뽑아 코드 중복을 줄이는 도구이며, 실제로는 인스턴스 내부에 부모·자식 영역이 함께 생성되는 메모리 구조로 구현된다.
  • 메서드/필드 탐색은 항상 "호출에 쓰인 타입에서 시작해서, 없으면 부모로 올라간다"는 규칙을 따른다 — 오버라이딩·다형성의 토대.
  • super는 이름이 겹칠 때 부모를 명시적으로 가리키는 키워드이며, 특히 생성자에서는 "부모 먼저 초기화"를 강제하는 필수 규칙으로 등장한다.
  • final은 클래스에 걸면 상속 자체를 막고, 메서드에 걸면 오버라이딩을 막는다 — 접근 제어자와 함께 "의도치 않은 변경을 막는" 자바의 대표적 제약 장치들이다.
