3. 객체 지향 프로그래밍

인프런 김영한 강사님의 "김영한의 실전 자바 - 기본편" 강의를 듣고 정리한 학습 노트입니다. 강의 PDF를 그대로 옮긴 것이 아니라, 강의에서 설명한 흐름과 예시를 제 나름대로 재구성했습니다.

절차 지향 vs 객체 지향

  • 절차 지향 프로그래밍: 이름 그대로 절차(실행 순서)를 지향한다. "어떻게 동작할까"에 초점을 맞추고, 데이터와 그 데이터를 처리하는 로직이 서로 분리되어 있다. 지금까지 작성해온 코드는 클래스와 객체를 썼더라도 전부 절차 지향이었다.
  • 객체 지향 프로그래밍: 객체를 지향한다. "무엇이 있어야 하고, 그 속성과 기능을 어떻게 하나로 묶을까"에 초점을 맞춘다 — 데이터(속성)와 그 데이터를 다루는 메서드(기능)가 하나의 객체 안에 함께 들어간다.
  • 둘은 서로 대립하는 개념이 아니라 초점의 차이다. 단순히 클래스로 데이터를 묶었다고 객체 지향이 되는 게 아니라, 그 데이터를 다루는 기능까지 같은 클래스 안에 들어가야 진짜 객체 지향이다.

절차 지향으로 시작 — 음악 플레이어 예제

  • 1단계: volume, isOn을 지역 변수로 두고 순서대로 켜기 → 볼륨 조절 → 상태 확인 → 끄기를 처리 — 전형적인 절차 지향.
  • 2단계(데이터 묶음): MusicPlayerData 클래스를 만들어 volume, isOn을 멤버 변수로 묶는다. 데이터가 한 곳에 모이니 프로그램이 복잡해져도 어디서 찾을지 명확해진다 — 하지만 여전히 이 데이터를 조작하는 로직은 Main 쪽에 별도로 남아있다.
  • 3단계(메서드 추출): 반복되는 켜기/끄기/볼륨 조절/상태 출력 로직을 각각 메서드로 뽑아낸다. 중복이 줄고 가독성이 좋아지지만, 데이터는 MusicPlayerData 클래스에, 기능은 Main 클래스의 메서드에 여전히 나뉘어 있다는 근본 문제는 남는다.
  • 데이터와 기능이 이렇게 다른 곳에 있으면, 데이터가 바뀔 때마다 그 데이터를 다루는 기능 코드도 같이 찾아가 고쳐야 한다 — 관리 포인트가 두 곳으로 늘어나는 유지보수의 약점.

클래스와 메서드 — 데이터와 기능을 한 곳에

  • 클래스는 멤버 변수(데이터)뿐 아니라 메서드(기능)도 가질 수 있다. 외부의 별도 메서드로 값을 조작하던 것을, 그 값을 가진 클래스 내부에 메서드로 넣어버리면 데이터와 기능이 한 클래스에 응집된다.
  • static이 없는 메서드는 원칙적으로 객체를 먼저 생성해야 호출할 수 있다. 인스턴스 메서드 안에서는 this.value처럼 자기 자신의 멤버 변수에 접근할 수 있다.
  • 이렇게 속성과 기능을 하나로 묶는 것이 객체 지향 프로그래밍의 본질이다.
class ValueData {
    int value;

    void add() {
        this.value++; // 자기 자신의 멤버 변수에 접근
    }
}

ValueData data = new ValueData();
data.add(); // 객체를 생성해야 메서드 호출 가능

MusicPlayer를 온전한 객체로

  • MusicPlayer 클래스 하나에 volume, isOn 속성과 on(), off(), volumeUp(), volumeDown(), showStatus() 기능을 전부 담는다 — 이 클래스 하나만 있으면 완전한 음악 플레이어를 만들 수 있다.
  • 사용하는 쪽(MusicPlayerMain)은 player.on(), player.volumeUp()처럼 메서드만 호출하면 된다 — 내부에 volume이 어떻게 저장되고 계산되는지 몰라도 실제 음악 플레이어를 쓰듯 자연스럽게 쓸 수 있다.
class MusicPlayer {
    int volume;
    boolean isOn;

    void on() { isOn = true; }
    void off() { isOn = false; }
    void volumeUp() { volume++; }
    void volumeDown() { volume--; }
    void showStatus() {
        System.out.println("음악 플레이어 상태: " + isOn + ", 볼륨: " + volume);
    }
}

MusicPlayer player = new MusicPlayer();
player.on();
player.volumeUp();
player.showStatus();

캡슐화

  • 속성과 기능을 하나의 클래스로 묶어, 필요한 기능만 메서드로 외부에 제공하는 것을 캡슐화라고 한다 — 데이터와 그 데이터를 다루는 기능이 하나의 캡슐 안에 들어있는 셈이다.
  • 캡슐화의 실익은 변경에 강해진다는 것 — 클래스 내부의 멤버 변수 이름(예: volume → volume2)을 바꿔도, 외부에서는 여전히 volumeUp()만 호출하므로 사용하는 쪽 코드는 전혀 손댈 필요가 없다. 내부 구현(볼륨을 2씩 올리도록 바꾸는 등)도 마찬가지로 클래스 내부만 고치면 끝난다.
  • 반대로 외부에 공개된 메서드의 이름이나 시그니처(예: volumeUp → volumeUp2)를 바꾸면, 그 메서드를 호출하는 모든 곳을 찾아 함께 고쳐야 한다 — 그래서 공개 기능(메서드)의 이름은 함부로 바꾸기 어렵고, 반대로 숨겨진 내부 데이터는 자유롭게 바꿀 수 있어야 좋은 설계다.

정리

  • 절차 지향은 "어떻게 실행할까"(순서), 객체 지향은 "무엇이 있어야 하고 속성·기능을 어떻게 묶을까"(구조)에 초점을 둔다 — 둘은 우열이 아니라 관점의 차이다.
  • 세상 모든 사물은 속성(데이터)과 기능(행동)으로 추상화할 수 있다 — 자동차는 색상·속도(속성)와 액셀·브레이크(기능), 게임 캐릭터는 레벨·경험치(속성)와 이동·공격(기능)을 가진다. 객체 지향은 이 방식을 그대로 프로그램에 옮긴 것이다.
  • 데이터를 클래스로 묶는 것만으로는 부족하고, 그 데이터를 다루는 메서드까지 같은 클래스에 넣어야 진짜 객체 지향이 된다.
  • 캡슐화 덕분에 클래스 내부 구현은 자유롭게 바꾸면서도, 외부에 공개한 메서드 이름만 유지하면 사용하는 쪽 코드에 영향을 주지 않을 수 있다 — 이후 다룰 상속·다형성·추상화 같은 객체 지향의 다른 특징들도 이 캡슐화 위에서 쌓인다.
