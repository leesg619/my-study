김영한의 실전 자바 - 중급 1편

1. Object 클래스

인프런 김영한 강사님의 "김영한의 실전 자바 - 중급 1편" 강의를 듣고 정리한 학습 노트입니다. 강의 PDF를 그대로 옮긴 것이 아니라, 강의에서 설명한 흐름과 예시를 제 나름대로 재구성했습니다.

java.lang 패키지

  • 자바 언어 자체를 이루는 가장 기본 클래스 모음 (Object, String, 래퍼 타입, Class, System 등).
  • 모든 자바 프로그램에서 자동 임포트되므로 import 구문이 필요 없다 — 그만큼 언어 자체의 일부로 취급된다는 뜻.
  • 이 패키지를 이해하는 것 = 자바라는 언어 자체를 이해하는 것.

Object = 모든 클래스의 최상위 부모

  • 상속 관계를 끝까지 따라 올라가면 항상 Object가 나온다.
  • 묵시적 상속: extends를 안 적어도 컴파일러가 자동으로 Object를 상속시켜 준다 (개발자가 코드로 적지 않아도 시스템이 처리).
  • 명시적 상속: 개발자가 직접 extends로 적는 것. extends Object는 어차피 자동으로 되므로 생략하는 게 관례.
  • 예: Parent extends Object(묵시적) → Child extends Parent(명시적) 라면, Child는 Parent를 거쳐 Object의 toString()까지 그대로 물려받는다. Child·Parent 어디에도 toString()을 작성한 적이 없어도 호출되는 이유.

Object가 최상위인 이유

  • 모든 객체에게 필요한 공통 기능(정보 제공, 비교 등)을 한곳에서 제공 — 매번 새로 안 만들어도 됨.
  • 모든 객체를 Object 타입 하나로 다룰 수 있게 해서, 다형성의 기반이 됨.

Object 다형성 — 장점과 한계

  • 서로 관계없는 Dog, Car도 결국 Object를 상속받으므로, Object 타입 변수 하나로 둘 다 참조 가능.
  • 장점: 매개변수 타입을 Object로 잡으면 어떤 객체든 다 받을 수 있어 유연함.
  • 한계: Object는 자기 자신이 가진 기능만 알기 때문에, obj.sound()처럼 Dog만의 메서드는 호출 불가 (컴파일 오류).
  • 해결: instanceof로 타입 확인 후 다운 캐스팅. 다운 캐스팅은 객체 자체를 바꾸는 게 아니라 "어떤 타입으로 바라볼지"만 바꾸는 것.
Object obj = new Dog();

if (obj instanceof Dog) {
    Dog d = (Dog) obj;
    d.sound();  // 다운 캐스팅 후에만 호출 가능
}
  • 제대로 된 다형성 활용 = 다형적 참조(부모 타입으로 여러 자식 참조) + 메서드 오버라이딩(자식이 부모 메서드 재정의).
  • Dog 고유 기능은 다운 캐스팅 없이는 못 쓰지만, Object에 이미 정의된 toString()은 오버라이딩만으로 다형성을 그대로 누릴 수 있다.

Object 배열

  • Object는 모든 타입을 담을 수 있으므로, Object[] 하나면 Dog든 Car든 종류 상관없이 담을 수 있다.
  • Object[]를 받는 메서드는 새로운 클래스가 추가돼도 코드를 고칠 필요가 없다 (재사용성).
  • 만약 Object 같은 공통 개념이 없었다면 → 모든 객체를 받는 배열/메서드를 만들 수 없어서 개발자마다 비슷한 걸 각자 만들고 서로 호환도 안 됐을 것.

toString()

  • 기본 Object.toString()은 클래스이름@16진수참조값 형태 문자열을 반환.
  • System.out.println(obj)는 내부적으로 obj.toString()을 호출하는 것과 같다 — 오버라이딩 안 하면 의미 없는 참조값만 출력됨.
  • 객체 상태(필드 값)를 보여주려면 오버라이딩 필요. 직접 조립하기보다 IDE의 "Generate toString()"을 쓰는 게 안전하고 빠름.
  • ObjectPrinter.print(Object obj)처럼 Object를 받는 메서드에 넘기면, 실행 시점에 각 클래스가 오버라이딩한 toString()이 호출된다 (다형성).
  • 오버라이딩 후 원래 참조값이 필요하면 Integer.toHexString(System.identityHashCode(obj))로 얻을 수 있음.
class Dog {
    String name;

    @Override
    public String toString() {
        return "Dog{name='" + name + "'}";
    }
}

Object와 OCP (개방-폐쇄 원칙)

  • Object·toString()이 없다면: Car는 carInfo(), Dog는 info()처럼 클래스마다 제각각인 메서드가 생기고, 출력 담당 클래스는 각 클래스에 맞춰 분기해야 함 → 새 클래스 추가마다 수정 필요 (OCP 위반).
  • Object 타입으로 매개변수를 받고 각 클래스가 toString()을 오버라이딩하게 하면, 출력 담당 클래스는 구체 클래스(Car, Dog)가 아니라 추상적인 Object에만 의존하게 됨.
  • 여기서 "추상적"이란 추상 클래스·인터페이스만이 아니라, Animal과 Dog·Cat의 관계처럼 "더 상위 개념"이라는 뜻으로 넓게 이해.
  • 결과: 새 클래스를 추가하고 그 클래스의 toString()만 채우면 되고, 출력 담당 코드는 손댈 필요 없음 — 확장에는 열려 있고 변경에는 닫혀 있는 OCP.
  • System.out.println이 어떤 프로젝트·어떤 객체에도 수정 없이 동작하는 이유가 바로 이 원리(다형적 참조 + 메서드 오버라이딩).

equals() — 동일성과 동등성

  • 동일성(identity): ==로 비교. 완전히 같은 메모리의 같은 인스턴스인지(참조값 비교).
  • 동등성(equality): equals()로 비교. 인스턴스는 달라도 논리적으로 같은 값인지.
  • 예: 회원 번호가 같은 두 User 인스턴스는 물리적으로 다른 객체(동일성 없음)지만, 논리적으로는 같은 회원(동등성 있음)일 수 있다.
  • 주의: 기본 Object.equals()는 내부적으로 ==와 동일하게 동작한다 — 오버라이딩 없이 필드 값이 같은 두 객체를 비교하면 false가 나옴. Object는 어떤 필드를 기준으로 "논리적으로 같다"고 볼지 알 수 없기 때문.

equals() 구현

class UserV2 {
    String id;

    @Override
    public boolean equals(Object obj) {
        UserV2 other = (UserV2) obj;
        return this.id.equals(other.id);  // String 비교는 == 아닌 equals()
    }
}
  • 매개변수 타입이 Object이므로 id에 접근하려면 UserV2로 다운 캐스팅 필요.
  • 위 코드는 최소 버전 — 실제로 안전한 equals()는 null 체크, 클래스 타입 체크, 반사성·대칭성·추이성·일관성 규칙까지 지켜야 해서 손으로 짜기 까다롭다.
  • 실무 팁: 규칙을 다 외우기보다 IDE의 equals/hashCode 자동 생성 기능을 활용하는 게 낫다.
  • equals()는 모든 클래스에 필요한 게 아니라, 논리적 동등성 비교가 실제로 필요한 클래스에서만 오버라이딩.
  • equals()와 짝을 이루는 hashCode()는 컬렉션 프레임워크에서 더 다룰 내용.

정리

  • Object는 모든 클래스가 묵시적으로 상속받는 최상위 부모.
  • Object 타입으로 다양한 객체를 다룰 수 있지만(다형적 참조), 고유 메서드를 쓰려면 다운 캐스팅 필요.
  • Object[]는 어떤 타입이든 담을 수 있어 새 클래스 추가에도 코드 변경 불필요.
  • toString()은 println이 내부에서 자동 호출 — 의미 있는 정보를 보려면 오버라이딩 필요.
  • 다형적 참조 + 메서드 오버라이딩 = OCP를 실현하는 핵심 메커니즘 (System.out.println이 실제 사례).
  • 동일성(==)과 동등성(equals())은 다르다. 기본 equals()는 동일성과 같게 동작하므로, 논리적 비교가 필요하면 오버라이딩.
  • 정확한 equals() 구현은 규칙이 많아 IDE 자동 생성 활용이 현실적.
