Set을 직접 만들어 보면 — 왜 해시가 필요한가

인덱스가 없으니 구현할 건 단순하다: add(중복이면 거부), contains(있는지 확인), remove.

public class MyHashSetV0 {
    private int[] elementData = new int[10];
    private int size = 0;

    public boolean add(int value) {   // O(n)
        if (contains(value)) {
            return false;
        }
        elementData[size] = value;
        size++;
        return true;
    }

    public boolean contains(int value) { // O(n)
        for (int data : elementData) {
            if (data == value) {
                return true;
            }
        }
        return false;
    }
}
  • 문제: contains가 전부 뒤지는 O(n)이고, 중복 확인 때문에 add까지 O(n)이 된다.
  • 값을 넣을 때마다 전체를 훑어야 하니 데이터가 많으면 사실상 쓸 수 없다 → 중복 찾기가 성능의 발목을 잡는다. 이걸 평균 O(1)로 끌어올리는 게 해시 알고리즘이다.

해시 알고리즘을 단계별로

1단계 — 값을 인덱스로 쓴다

  • 배열은 인덱스 접근이 O(1)인데, 검색할 때는 그 장점을 못 쓴다. 인덱스와 데이터 값이 아무 관계가 없기 때문이다.
  • 아이디어: 값 자체를 인덱스로 맞춰 저장한다. inputArray[8] = 8처럼 넣으면, 8을 찾을 때 inputArray[8]만 보면 된다 → 검색이 O(1).

2단계 — 메모리 낭비의 벽

  • 입력 범위가 0~99면 값 6개만 넣어도 크기 100짜리 배열이 필요하고 나머지 94칸은 null이다.
  • int 전체 범위(약 42억 가지)라면 4byte만 해도 약 17GB의 배열이 필요하다 → 속도를 얻는 대신 공간을 너무 많이 쓴다. 트레이드오프가 감당이 안 된다.

3단계 — 나머지 연산으로 범위를 좁힌다

static final int CAPACITY = 10;

static int hashIndex(int value) {
    return value % CAPACITY;
}

// 1→1, 2→2, 5→5, 8→8, 14→4, 99→9
inputArray[hashIndex(14)] = 14;

int result = inputArray[hashIndex(14)]; // 검색도 같은 계산으로 O(1)
  • 값을 배열 크기로 나눈 나머지는 절대 배열 크기를 넘지 않는다 → 어떤 값이든 안전한 인덱스로 바꿀 수 있다.
  • 이렇게 값을 변환해서 얻은 인덱스를 해시 인덱스(hashIndex)라고 한다.
  • 저장과 조회 모두 "해시 인덱스 계산 → 배열 접근"이므로 O(1). 공간도 크게 절약된다.

4단계 — 해시 충돌

  • 9와 99는 둘 다 나머지가 9다. 다른 값이 같은 해시 인덱스를 갖는 현상이 해시 충돌 → 그냥 넣으면 먼저 저장한 값이 덮어써져 사라진다.
  • CAPACITY를 입력 범위만큼 늘리면 충돌은 없어지지만, 다시 메모리 낭비로 돌아간다.
  • 발상의 전환: 충돌은 일어날 수 있다고 인정한다. 대신 한 칸에 여러 값을 담을 수 있게 만든다.
    • 저장: 해시 인덱스 칸에 있는 작은 자료 구조에 값을 함께 넣는다. 9번 칸 → [99, 9].
    • 조회: 해시 인덱스 칸으로 간 다음, 그 안의 값을 하나씩 비교한다.
  • 최악의 경우(모든 값이 한 칸에 몰림: 9, 19, 29, 99…)에는 O(n)이지만, 값은 대체로 고르게 퍼지므로 한 칸에 있는 몇 개만 비교하면 된다 → 평균 O(1).

충돌까지 구현하기

LinkedList<Integer>[] buckets = new LinkedList[CAPACITY];
for (int i = 0; i < CAPACITY; i++) {
    buckets[i] = new LinkedList<>();
}

private static void add(LinkedList<Integer>[] buckets, int value) {
    int hashIndex = hashIndex(value);
    LinkedList<Integer> bucket = buckets[hashIndex]; // O(1)
    if (!bucket.contains(value)) {                   // 평균 O(1), 최악 O(n)
        bucket.add(value);
    }
}

private static boolean contains(LinkedList<Integer>[] buckets, int searchValue) {
    int hashIndex = hashIndex(searchValue);
    return buckets[hashIndex].contains(searchValue);
}
  • 배열의 각 칸에 값이 아니라 자료 구조(연결 리스트)가 들어 있다. 이걸 바구니에 비유해 버킷(bucket)이라 부른다.
  • 중복 체크와 검색은 그 칸의 바구니만 뒤지면 된다 — 전체를 훑지 않는다.

CAPACITY와 충돌 확률

  • 배열이 작으면 충돌이 잦아 연결 리스트가 길어지고 성능이 떨어진다. 너무 크면 메모리가 낭비된다.
  • 통계적으로 입력 데이터 수가 배열 크기의 75%를 넘지 않으면 충돌이 비교적 적다 → 낭비와 성능 사이의 적당한 기준선.

정리

  • 값 → (나머지 연산) → 해시 인덱스 → 배열 접근. 이 흐름으로 검색을 O(n)에서 평균 O(1)로 바꾼다.
  • 충돌은 없앨 수 없으므로 인정하고, 버킷으로 해결한다. 최악은 O(n)이지만 드물다.
