3. String 클래스

인프런 김영한 강사님의 "김영한의 실전 자바 - 중급 1편" 강의를 듣고 정리한 학습 노트입니다. 강의 PDF를 그대로 옮긴 것이 아니라, 강의에서 설명한 흐름과 예시를 제 나름대로 재구성했습니다.

String 클래스 기본

  • char는 문자 하나만 담는 기본형이라, 여러 문자를 다루려면 char[]를 써야 하는데 이건 다루기 불편하다. 자바는 그 불편함을 해소하려고 String을 제공한다.
  • 생성 방법 두 가지: 리터럴(String s1 = "hello";)과 new String("hello"). 리터럴도 사실 내부적으로는 new String()과 개념적으로 같은 객체 생성으로 처리된다.
  • String은 public final class로, 내부에 실제 문자열 데이터를 char[](Java 9 이전) 또는 byte[](Java 9 이후, 메모리 효율을 위해)로 감춰서 들고 있다.
  • String은 기본형이 아니라 참조형이다. + 연산자로 문자열을 이어붙이는 건 자바 언어가 특별히 허용해준 문법 — 원래 참조값끼리는 +를 할 수 없다.

String 클래스 비교 — == 대신 equals()

  • new String("hello")로 만든 두 객체는 값이 같아도 ==로 비교하면 참조값이 달라서 false. equals()로 비교해야 true가 나온다.
  • String은 Object.equals()를 오버라이딩해서 참조값이 아니라 내부 문자열 값을 비교하도록 만들어져 있다.
  • 그런데 문자열 리터럴끼리는 얘기가 다르다 — 자바는 성능 최적화를 위해 문자열 풀(String Pool)이라는 공간에 리터럴을 저장해두고, 같은 리터럴이 또 나오면 새로 안 만들고 기존 인스턴스를 재사용한다. 그래서 String s3 = "hello"; String s4 = "hello";는 == 비교에서도 true가 나올 수 있다.
  • 문제는 메서드를 작성하는 입장에서 매개변수로 들어온 문자열이 new로 만들어졌는지 리터럴(풀에서 왔는지) 알 방법이 없다는 것 — 그래서 문자열 비교는 항상 equals()를 써야 한다.

String은 불변 객체

  • String은 앞서 배운 불변 객체의 대표 사례다 — 생성 후 내부 값을 절대 바꿀 수 없다 (필드가 final).
  • str.concat("java")를 호출해도 str 자체는 안 바뀐다. concat()은 기존 문자열은 그대로 두고 합쳐진 새 String 객체를 만들어 반환할 뿐이다.
  • 왜 불변으로 설계했나: 문자열 풀에서 여러 변수가 같은 인스턴스를 공유하는데, 만약 String이 가변이었다면 한 변수의 값 변경이 풀을 공유하는 다른 모든 변수에 사이드 이펙트를 일으켰을 것. 불변이기 때문에 풀을 안전하게 재사용할 수 있다.

주요 메서드

  • 메서드가 워낙 많아서 다 외우기보다는, 자주 쓰는 것 위주로 익히고 필요할 때 검색하는 게 현실적이다.
  • 정보 조회: length(), isEmpty()(완전히 빈 문자열만 true), isBlank()(공백만 있어도 true), charAt(i)
  • 비교: equals(), equalsIgnoreCase(), compareTo()(사전순 비교, 음수/0/양수 반환), startsWith()/endsWith()
  • 검색: contains(), indexOf()(처음 등장 위치), lastIndexOf()(마지막 등장 위치)
  • 조작/변환: substring(), concat()(+와 동일하게 동작), replace()/replaceFirst(), toUpperCase()/toLowerCase()
  • 공백 제거: trim()은 스페이스만, strip()(Java 11+)은 유니코드 공백까지 제거 — stripLeading()/stripTrailing()으로 한쪽만도 가능.
  • 분할/조합: split()은 정규식 기준으로 배열로 쪼개고, String.join(delimiter, ...)은 그 반대 — 직접 구분자를 이어붙이는 것보다 훨씬 간결하다.
  • 변환: String.valueOf(obj)(객체는 내부적으로 toString() 호출), toCharArray(), String.format()/printf()(%d, %s, %.2f 같은 형식 지정자), matches()(정규식 검증)
  • CharSequence는 String과 StringBuilder의 상위 타입 — replace, join 같은 메서드가 둘 다 인자로 받을 수 있는 이유.

StringBuilder — 가변 String

  • String은 불변이라 값을 더하거나 바꿀 때마다 새 객체가 생기고, 쓰지 않게 된 중간 객체는 GC 대상이 된다 — 변경이 잦으면 CPU·메모리를 많이 잡아먹는다.
  • StringBuilder는 내부 배열이 final이 아니라서 값을 직접 수정할 수 있는 가변 문자열이다. 새 객체를 안 만들고 내부 상태를 바꾸므로 훨씬 효율적.
  • 주요 메서드: append()(추가), insert()(위치 삽입), delete()(삭제), reverse()(뒤집기), 마지막에 toString()으로 String으로 변환.
  • 권장 패턴: 변경이 잦은 동안은 StringBuilder로 작업하고, 다 끝나면 toString()으로 String으로 바꿔서 사이드 이펙트 없이 안전하게 쓴다.
StringBuilder sb = new StringBuilder();
sb.append("hello").append(" ").append("java");
String result = sb.toString(); // "hello java"

String 최적화

  • 리터럴끼리의 +는 컴파일러가 자동으로 합쳐버려서 런타임 비용이 없다. 변수를 더하는 것도 자바가 내부적으로 StringBuilder 등을 써서 알아서 최적화해준다.
  • 문제는 반복문 안에서 문자열을 +로 계속 이어붙일 때다 — 컴파일러가 반복 횟수를 예측할 수 없어서 최적화가 안 먹히고, 매 반복마다 새 String 객체가 생겨서 성능이 크게 떨어진다 (10만 번에 2.5초).
  • 이럴 때 StringBuilder를 직접 써서 반복문 밖에서 만들고 안에서 append()만 하면 같은 작업이 3ms로 끝난다 (약 700~800배 차이).
  • StringBuilder 직접 사용을 고려할 때: 반복문에서 문자열을 계속 이어붙일 때, 조건문으로 동적으로 조립할 때, 긴 문자열의 특정 부분을 자주 바꿀 때.
  • StringBuffer는 StringBuilder와 기능은 같지만 내부에 동기화가 있어 멀티스레드에는 안전하지만 그만큼 느리다 — 특수한 멀티스레드 상황이 아니면 StringBuilder가 기본 선택.

메서드 체이닝

  • 메서드 체이닝: 메서드가 자기 자신(this)을 반환하도록 만들어서, 반환값에 바로 다음 메서드를 이어서 호출하는 기법.
  • StringBuilder.append()가 대표 사례 — append()가 StringBuilder 자신을 반환하기 때문에 sb.append("a").append("b").reverse()처럼 한 줄로 이어 쓸 수 있다.
  • 체이닝이 되도록 메서드를 설계하는 쪽은 (반환 타입을 맞추는 등) 조금 더 신경 써야 하지만, 그 덕분에 사용하는 쪽 코드는 훨씬 간결해진다.

정리

  • String은 char[]/byte[]를 감싸서 문자열을 객체지향적으로 다루게 해주는 참조형이며 불변 객체다.
  • 문자열 비교는 항상 ==이 아니라 equals() — 리터럴은 문자열 풀 때문에 ==가 우연히 true가 나올 수도 있지만 믿을 방법이 없다.
  • concat() 등 값 변경처럼 보이는 메서드는 실제로는 새 String을 반환하는 것 — 반환값을 받아써야 한다.
  • 값 변경이 잦다면 불변인 String 대신 가변인 StringBuilder를 쓰고, 특히 반복문 안 문자열 연결에서는 성능 차이가 극명하다.
  • 메서드 체이닝(자기 자신을 반환)은 String·StringBuilder 모두에서 코드를 간결하게 만들어주는 패턴이다.
