11. 다형성2

인프런 김영한 강사님의 "김영한의 실전 자바 - 기본편" 강의를 듣고 정리한 학습 노트입니다. 강의 PDF를 그대로 옮긴 것이 아니라, 강의에서 설명한 흐름과 예시를 제 나름대로 재구성했습니다.

다형성 없이 — 동물 소리 예제의 한계

  • Dog, Cat, Cow를 상속 관계 없이 각자 독립적으로 만들면, 새 동물이 추가될 때마다 클래스 추가 + 소리 출력 코드 추가가 반복된다.
  • 중복을 줄여보려 해도 벽에 부딪힌다: soundCow(Cow cow) 같은 메서드는 Cat을 넘길 수 없고(타입 불일치 → 컴파일 오류), Cow[] 배열에도 Dog·Cat을 담을 수 없다.
  • 모든 시도가 실패하는 근본 원인은 타입이 서로 다르다는 것 — 만약 Dog·Cat·Cow가 같은 타입으로도 취급될 수 있다면 메서드나 배열로 깔끔하게 묶을 수 있을 것이라는 게 이 문제의 실마리이고, 이것이 다형적 참조로 이어진다.

다형성 적용 — 공통 부모로 묶기

  • 부모 Animal 클래스에 sound()를 정의하고, Dog·Cat·Cow가 이를 상속해 각자 오버라이딩한다.
  • void soundAnimal(Animal animal) { animal.sound(); } 하나만 있으면 충분하다 — Dog·Cat·Cow 인스턴스 모두 Animal 타입으로 업캐스팅되어 이 메서드에 전달될 수 있고(다형적 참조), animal.sound()는 실제로 넘어온 인스턴스에서 오버라이딩된 메서드가 실행된다(메서드 오버라이딩) — 섹션 10에서 배운 두 조각이 여기서 실전으로 합쳐진다.
  • 새 동물(Duck)을 Animal의 자식으로 추가하고 sound()만 오버라이딩하면, soundAnimal() 메서드는 단 한 줄도 고치지 않고 Duck까지 그대로 처리한다.
abstract class Animal {
    abstract void sound();
}
class Dog extends Animal { void sound() { System.out.println("멍멍"); } }
class Cat extends Animal { void sound() { System.out.println("야옹"); } }

static void soundAnimal(Animal animal) {
    animal.sound(); // 실제 인스턴스의 오버라이딩된 메서드가 실행
}

배열과 반복문으로 더 다듬기

  • Animal[] animals = {dog, cat, cow};처럼 부모 타입 배열에 서로 다른 자식 인스턴스를 함께 담고, for (Animal a : animals) a.sound();로 한 번에 순회할 수 있다.
  • 반복되는 순회 로직을 soundAnimal(Animal[] animals) 메서드로 추출(Extract Method)하면, 배열 순회 코드 자체가 재사용 가능한 하나의 도구가 된다.
  • 좋은 코드의 기준: 새 기능을 추가할 때 변경 범위가 최소화되는 코드. 다형성 이전엔 새 동물마다 출력 로직까지 건드려야 했지만(코드 여기저기를 고쳐야 하는 "샷건 효과"), 다형성 이후엔 배열에 인스턴스 하나 추가하는 것으로 끝난다.

남은 문제 — 추상 클래스로 해결

  • 지금 상태엔 두 가지 허점이 있다: ① Animal이 일반 클래스라면 new Animal()처럼 의도치 않게 직접 생성될 수 있다. ② 자식이 sound() 오버라이딩을 깜빡해도 컴파일러가 잡아주지 못한다 — 그러면 부모의 (의미 없는) sound()가 조용히 실행된다.
  • 추상 클래스(abstract class)로 선언하면 new Animal()이 컴파일 오류가 되어 ①이 해결된다.
  • 메서드 앞에 abstract를 붙이고 본문(바디)을 아예 없애면 추상 메서드가 된다 — 자식 클래스는 이 메서드를 반드시 오버라이딩해야 하며, 오버라이딩하지 않으면 그 자식도 추상 클래스여야 한다(그렇지 않으면 컴파일 오류) — ②가 해결된다.
  • 추상 메서드가 하나라도 있는 클래스는 반드시 abstract로 선언해야 한다는 규칙도 함께 따라온다.
  • "좋은 프로그램은 적절한 제약이 있는 프로그램" — 추상 클래스·추상 메서드는 실수로 부모를 직접 생성하거나 자식이 구현을 빼먹는 사고를 컴파일 시점에 막아주는 장치다.
abstract class Animal {
    abstract void sound(); // 바디 없음 — 자식이 반드시 구현
}
// new Animal(); // 컴파일 오류 — 추상 클래스는 생성 불가

순수 추상 클래스 → 인터페이스

  • 모든 메서드가 추상 메서드인 추상 클래스를 순수 추상 클래스라 부른다 — 부모로서 물려줄 실제 기능은 하나도 없고, 오직 "자식이 지켜야 할 규격"만 제공하는 껍데기 역할이다. USB 규격처럼, "이 모양대로 만들어야 한다"는 약속만 강제한다.
  • 자바는 이 순수 추상 클래스를 더 편하게 쓰도록 interface 키워드를 제공한다. 인터페이스의 메서드는 기본적으로 public abstract가 생략된 것이고, 필드는 자동으로 public static final(상수)이 된다.
  • 부모의 기능을 물려받는 것을 상속(extends)이라 부르는 반면, 인터페이스는 물려줄 기능이 없고 자식이 전부 채워 넣어야 하므로 구현(implements)이라 부른다 — 용어만 다를 뿐 자바 내부적으로는 클래스 파일로 컴파일되는 방식이 동일하다.
  • 인터페이스가 존재하는 진짜 이유는 제약이다 — 순수 추상 클래스는 이론상 실행 가능한 일반 메서드를 섞어 넣을 수도 있어 실수의 여지가 있지만, 인터페이스는 (Java 8의 default/private 메서드 같은 특수한 경우를 빼면) 오직 추상 메서드만 허용해 그 여지를 원천 차단한다.

인터페이스의 다중 구현

  • 클래스의 다중 상속은 다이아몬드 문제 때문에 금지되지만, 인터페이스는 여러 개를 동시에 implements 할 수 있다.
  • 이유는 단순하다 — 인터페이스 자체엔 실행 가능한 기능이 없기 때문. 두 인터페이스에 같은 이름의 메서드가 있어도, 그 기능을 실제로 채우는 건 항상 구현 클래스 하나뿐이므로 "어느 부모의 기능을 쓸지" 고민할 필요 자체가 없다 — 다이아몬드 문제가 발생할 조건이 애초에 성립하지 않는다.
  • class Child implements InterfaceA, InterfaceB처럼 여러 인터페이스를 구현하면, 그 인스턴스는 InterfaceA 타입으로도, InterfaceB 타입으로도 다형적으로 참조될 수 있다 — 어느 타입으로 부르든 결국 Child가 오버라이딩한 메서드가 실행된다.

클래스 상속과 인터페이스 구현을 함께 — 새/닭 예제

  • AbstractAnimal(추상 클래스, sound()는 추상·move()는 일반 메서드)과 Fly(인터페이스, fly())를 함께 정의한다.
  • Bird는 class Bird extends AbstractAnimal implements Fly처럼 클래스 상속(1개, extends)과 인터페이스 구현(여러 개 가능, implements)을 동시에 쓸 수 있다 — 문법적으로 extends가 implements보다 앞에 와야 한다.
  • Dog는 Fly를 구현하지 않았으므로 Fly 타입으로 취급될 수 없다 — void flyAnimal(Fly f) 같은 메서드에 Dog 인스턴스를 넘기면 컴파일 오류가 난다. 반면 Bird·Chicken은 AbstractAnimal 타입으로도 Fly 타입으로도 참조될 수 있다.
  • 정리: 클래스 상속은 최대 하나, 인터페이스 구현은 여러 개 가능 — 이 비대칭이 자바가 다중 상속 문제 없이도 유연한 다형성을 제공하는 방법이다.

정리

  • 다형성이 실전에서 힘을 발휘하는 방식: 서로 다른 타입을 공통 부모로 묶고(다형적 참조), 그 부모 타입 하나로 순회·처리하되 실제로는 각 자식의 오버라이딩된 동작이 실행된다(메서드 오버라이딩) — 그 결과 새 타입이 추가돼도 기존 코드는 거의 그대로 유지된다.
  • 추상 클래스·추상 메서드는 "부모를 실수로 직접 생성하는 것"과 "자식이 오버라이딩을 빼먹는 것"이라는 두 가지 흔한 실수를 컴파일 시점에 막아주는 제약 장치다.
  • 인터페이스는 순수 추상 클래스(모든 메서드가 추상)를 더 편리하게 쓰도록 만든 것이며, 실행 가능한 기능이 전혀 없기 때문에 다중 구현이 안전하게 허용된다.
  • 한 클래스는 extends로 부모 클래스 하나만, implements로 인터페이스는 여러 개 가질 수 있다.
