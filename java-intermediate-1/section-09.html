9. 예외 처리 1 - 이론

인프런 김영한 강사님의 "김영한의 실전 자바 - 중급 1편" 강의를 듣고 정리한 학습 노트입니다. 강의 PDF를 그대로 옮긴 것이 아니라, 강의에서 설명한 흐름과 예시를 제 나름대로 재구성했습니다.

예외 처리가 왜 필요한가 — 반환 값만으로 처리했을 때

  • 예제 설정: NetworkClient(connect/send/disconnect 제공) → NetworkService(이 세 단계를 묶어 sendMessage 하나로 노출) → Main(사용자 입력을 받아 서비스 호출).
  • 지켜야 할 두 규칙: connect 실패 시 send를 호출하면 안 됨, 중간에 뭐가 실패하든 disconnect는 반드시 호출(외부 자원은 GC가 못 치워주므로 명시적 해제 필요).
  • 1차 시도 — 각 메서드가 "success"/"connectError"/"sendError" 같은 문자열을 반환하고, 호출부에서 if (!result.equals("success"))로 분기해서 처리. isError()로 추출해도 여전히 정상 흐름과 예외 흐름이 코드 한 곳에 뒤섞여 있다.
  • 거기다 return으로 중간에 빠져나가 버리면 disconnect 호출이 누락되는 문제까지 겹친다 — 이걸 막으려면 if-else로 계속 분기를 감싸야 해서 코드가 점점 읽기 힘들어진다.
  • 결론: 반환 값 기반 처리는 근본적으로 "무엇이 정상 로직이고 무엇이 오류 처리인지"가 한눈에 안 들어온다 — 이 문제를 언어 차원에서 풀기 위해 예외 처리 메커니즘이 필요하다.

예외 계층 구조

  • 예외도 결국 객체이므로 최상위 부모는 Object — 그 아래 Throwable이 예외 계층의 실질적 최상위이고, 그 밑에 Exception과 Error가 있다.
  • Error: 메모리 부족 등 애플리케이션이 복구할 수 없는 시스템 레벨 문제 — 애플리케이션 코드에서 잡으려고 하면 안 된다.
  • Exception: 애플리케이션 로직에서 실질적으로 다루는 최상위 예외. RuntimeException을 제외한 Exception과 그 하위는 전부 체크 예외.
  • RuntimeException과 그 하위는 전부 언체크(unchecked) 예외 = 런타임 예외 — 이 둘은 사실상 같은 말로 쓰인다.
  • 상속 관계가 예외 처리에도 그대로 적용된다 — catch (RuntimeException e)로 잡으면 그 자식 예외들도 전부 잡힌다. 다만 Throwable을 통째로 잡으면 Error까지 잡혀버리므로, 애플리케이션 로직에서는 Exception부터 시작해야 한다.

예외 처리 기본 규칙

  • 예외는 "폭탄 돌리기"에 비유할 수 있다 — 발생하면 호출 스택을 따라 위로 전파되고, 누군가는 이걸 잡아서 처리하거나 처리 못 하면 계속 밖으로 던져야 한다.
  • client → service → main 구조에서 client가 못 잡으면 service로, service도 못 잡으면 main으로 전파되고, main까지 못 잡으면 JVM이 예외 로그를 출력하며 프로그램 자체가 종료된다 — 개발 중 콘솔에 빨간 스택 트레이스가 뜨고 멈추는 게 바로 이 상황.
  • 여기도 상속 규칙이 그대로 적용 — 부모 타입으로 catch/throws 하면 자식 예외까지 함께 처리·전파된다.

체크 예외

  • Exception을 상속하면 체크 예외가 된다. 보통 생성자에서 super(message)로 메시지를 Throwable의 detailMessage 필드에 저장해두고, getMessage()로 꺼내 쓴다.
  • throw는 실제로 예외 객체를 만들어서 "터뜨리는" 동작, throws는 메서드 시그니처에 붙여 "이 예외는 내가 처리 안 하고 밖으로 던진다"고 선언하는 것 — 이름은 비슷해도 역할이 다르다.
  • 체크 예외의 핵심 강제 규칙: try-catch로 잡거나 throws로 선언하거나 둘 중 하나를 반드시 해야 컴파일된다. 안 하면 컴파일 오류.
  • catch도 다형성이 적용된다 — catch (Exception e)로 MyCheckedException을 잡을 수 있다.
  • 장점: 개발자가 예외 처리를 깜빡하는 걸 컴파일 시점에 잡아주는 안전장치. 단점: 정말 사소한 예외까지 전부 throws나 try-catch로 다뤄야 해서 코드가 번거로워진다.
class MyCheckedException extends Exception {
    public MyCheckedException(String message) {
        super(message);
    }
}

void call() throws MyCheckedException {
    throw new MyCheckedException("문제 발생");
}

언체크 예외

  • RuntimeException을 상속하면 언체크 예외. 체크 예외와의 유일한 차이는 throws 선언이 필수가 아니라는 것 — 그 외 동작(잡거나, 못 잡으면 위로 전파되는 것)은 완전히 동일하다.
  • throws를 안 적어도 컴파일은 되고, 예외는 발생하면 그대로 상위 호출자에게 전파된다. IDE 힌트를 위해 throws를 명시적으로 적어둘 수는 있지만 강제는 아니다.
  • 장단점이 체크 예외와 정반대다: 신경 쓰기 싫은 예외를 무시하고 넘어갈 수 있어 코드가 간결해지는 게 장점, 반대로 예외 처리를 깜빡해도 컴파일러가 안 알려준다는 게 단점.
  • 현대 애플리케이션 개발에서는 체크 예외의 "매번 처리 강제"가 실무에서 너무 번거롭다는 이유로, 언체크 예외를 사용하는 쪽이 대세가 되었다.

정리

  • 반환 값으로 성공/실패를 표현하는 방식은 정상 흐름과 오류 처리가 코드에 뒤섞여 가독성이 떨어진다 — 이게 예외 처리 메커니즘이 필요한 이유.
  • 예외 계층: Object → Throwable → (Exception, Error). Error는 잡지 말 것, 애플리케이션 코드는 Exception부터 다룬다.
  • 예외의 기본 규칙은 단 두 가지 — 잡아서 처리하거나, 처리 못 하면 반드시 밖으로 던진다. 끝까지 못 잡으면 프로그램이 종료된다.
  • Exception을 상속하면 체크 예외(throws/try-catch 필수), RuntimeException을 상속하면 언체크 예외(throws 선택).
  • 체크 예외는 컴파일러가 처리 누락을 잡아주는 안전장치지만 번거롭고, 언체크 예외는 간결하지만 누락 위험이 있다 — 실무에서는 언체크 예외 쪽이 더 널리 쓰인다.
