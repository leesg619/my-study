김영한의 실전 자바 - 중급 1편

6. 날짜와 시간

인프런 김영한 강사님의 "김영한의 실전 자바 - 중급 1편" 강의를 듣고 정리한 학습 노트입니다. 강의 PDF를 그대로 옮긴 것이 아니라, 강의에서 설명한 흐름과 예시를 제 나름대로 재구성했습니다.

날짜/시간 라이브러리가 필요한 이유

  • 날짜 계산은 겉보기와 다르게 매우 복잡하다 — 윤년(4년마다, 그런데 100년 단위는 예외, 400년 단위는 다시 예외), 서머타임(나라·지역마다 적용 여부와 기간이 다름), 타임존(지역마다 UTC 대비 오프셋이 다르고 서머타임까지 겹치면 더 복잡)이 얽혀 있다.
  • 직접 날짜 계산 로직을 짜면 거의 확실히 어딘가 틀린다 — 그래서 잘 만들어진 라이브러리를 쓰는 게 사실상 필수다.
  • 자바의 역사: java.util.Date(JDK 1.0, 타임존 지원 부족·가변 객체) → java.util.Calendar(JDK 1.1, 여전히 복잡하고 가변) → 오픈소스 Joda-Time(사용성 개선, 표준은 아님) → java.time(Java 8, Joda-Time 개발자가 참여해 만든 표준 API, 불변 객체로 설계).
  • 실용적인 오픈소스가 검증되고 나서 표준이 되는 패턴은 ORM 쪽의 Hibernate → JPA 관계와도 닮아있다.

클래스 한눈에 보기

  • LocalDate/LocalTime/LocalDateTime: "로컬" = 특정 지역의 시간대를 고려하지 않는다는 뜻. 국내 서비스처럼 단일 시간대만 다루면 충분.
  • ZonedDateTime: LocalDateTime + 타임존 정보(ZoneId) — 서머타임까지 자동으로 고려한다. 해외와 시간 약속을 잡거나 사용자에게 실제 현지 시간을 보여줄 때 적합.
  • OffsetDateTime: ZonedDateTime에서 ZoneId 대신 UTC 대비 고정 오프셋만 갖는다 — 서머타임을 반영하지 않는다.
  • Instant: UTC 기준 1970-01-01 00:00:00부터 흐른 시간을 초 단위로만 표현하는 "기계 중심" 시간.
  • Period(연/월/일 간격), Duration(시/분/초 간격) — "특정 시점"이 아니라 "시간의 양"을 표현.

기본 날짜/시간 — LocalDateTime

  • LocalDate.now()/LocalDate.of(y, m, d), LocalTime.now()/LocalTime.of(h, m, s)로 생성.
  • LocalDateTime은 내부에 LocalDate와 LocalTime을 그대로 들고 있는 구조 — toLocalDate()/toLocalTime()으로 쪼개거나 LocalDateTime.of(date, time)으로 다시 합칠 수 있다.
  • 모두 불변 객체다 — plusDays() 등은 원본을 바꾸지 않고 새 인스턴스를 반환하므로 반환값을 반드시 받아야 한다.
  • 비교: isBefore()/isAfter()는 이름 그대로. isEqual()은 타임존이 달라도 "시간적으로 같으면" true, equals()는 타입·타임존 등 내부 구성까지 완전히 같아야 true — 단순히 시간이 같은지 보고 싶으면 isEqual()이 맞다.
LocalDateTime dt = LocalDateTime.of(2024, 1, 1, 9, 0, 0);
LocalDateTime later = dt.plusDays(10); // dt는 그대로, later가 새 객체

타임존 — ZonedDateTime

  • ZoneId.of("Asia/Seoul")처럼 문자열로 타임존을 얻는다. ZoneId.getAvailableZoneIds()로 전체 목록을, ZoneId.systemDefault()로 현재 시스템의 기본 타임존을 조회할 수 있다.
  • ZonedDateTime = LocalDateTime + ZoneId. withZoneSameInstant(다른Zone)을 쓰면 "동일한 순간"을 다른 타임존 기준 시각으로 바꿔준다 (시각 자체가 그 지역 기준으로 재계산됨).
  • OffsetDateTime은 ZoneOffset.of("+09:00")처럼 고정 오프셋만 사용 — 서머타임 자동 반영이 없다.
  • 선택 기준: 실제 사용자 경험(회의 시간, 기념일 등)엔 ZonedDateTime, 로그 기록처럼 오프셋만 필요하고 서머타임을 신경 쓸 필요가 없으면 OffsetDateTime.

기계 중심의 시간 — Instant

  • 에포크 시간(유닉스 타임스탬프): 1970-01-01 00:00:00 UTC부터 경과한 초. Instant는 내부에 이 초(+나노초)만 가지고 있다.
  • 장점: 항상 UTC 기준이라 시간대에 독립적 — 전 세계 서버 로그를 같은 기준으로 남기거나, 서버 간 시간 동기화 기준점으로 쓰기 좋다.
  • 단점: 사람이 읽기엔 불편하고, 날짜 계산 기능이 빈약하다(초 단위만 있어서 분·시간으로 바꾸려면 계산이 필요).
  • Instant.now(), Instant.from(zonedDateTime)(단, LocalDateTime은 타임존 정보가 없어서 변환 불가), Instant.ofEpochSecond(n), getEpochSecond().
  • 실무 기준: 기본은 LocalDateTime, 국제화가 필요하면 ZonedDateTime, UTC 기준 절대시간이 필요하면 Instant.

기간, 시간의 간격 — Period, Duration

  • 시간은 "특정 시점"(예: 2024-01-01)과 "시간의 양"(예: 3개월)으로 나뉜다 — 전자는 LocalDateTime류, 후자는 Period/Duration.
  • Period(연/월/일): Period.ofDays(10)으로 생성, date.plus(period)로 날짜에 더하기, Period.between(start, end)로 두 날짜 사이 간격 계산.
  • Duration(시/분/초): Duration.ofMinutes(30), Duration.between(start, end)로 두 시간 사이 차이 계산.
  • 메서드 이름 규칙: Period는 getYears()처럼 내부 값을 그대로 꺼내니 get, Duration은 내부에 초만 있어서 시/분으로 보려면 계산이 필요하니 toHours()/toMinutes()처럼 to를 쓴다.

핵심 인터페이스 — Temporal, ChronoUnit, ChronoField

  • TemporalAccessor(읽기 전용, get()) ← Temporal(읽기+쓰기, plus()/minus()도 가능) — LocalDateTime·ZonedDateTime·Instant 등이 구현.
  • TemporalAmount — Period·Duration이 구현. "시간의 양"을 나타내는 쪽.
  • ChronoUnit(TemporalUnit 구현체): SECONDS, DAYS 등 "단위" — ChronoUnit.SECONDS.between(a, b)처럼 두 시점 차이를 특정 단위로 구할 때 쓴다.
  • ChronoField(TemporalField 구현체): YEAR, DAY_OF_MONTH 등 "필드" — 날짜·시간 구조 안의 한 항목을 가리킨다.
  • 이 인터페이스들 덕분에 LocalDate든 ZonedDateTime이든 get()/plus()/minus()를 똑같은 방식으로 쓸 수 있다 — 일관성 있는 API 설계의 예.

날짜/시간 조회하고 조작하기

  • 조회: dt.get(ChronoField.YEAR)처럼 ChronoField로 직접 조회하거나, getYear()/getMonthValue() 같은 편의 메서드를 쓴다. 편의 메서드가 없는 필드(예: 하루 중 몇 번째 분)는 get(ChronoField.MINUTE_OF_DAY)처럼 직접 지정.
  • 조작: dt.plus(10, ChronoUnit.YEARS)처럼 단위를 지정해서 더하거나, Period/Duration 객체를 만들어 plus()에 넘길 수도 있다. 당연히 불변이라 반환값을 받아야 한다.
  • 타입이 지원하지 않는 필드를 조회하면 UnsupportedFieldException이 발생한다(예: LocalDate에서 초 단위 조회). 미리 isSupported()로 확인하면 예외를 피할 수 있다.
  • with(ChronoField.YEAR, 2020): 특정 필드 하나만 바꾼 새 객체를 만든다 ("커피 with 시럽"처럼 기존 것에 하나를 얹는 느낌).
  • 복잡한 계산(다음 주 금요일, 이번 달 마지막 일요일 등)은 직접 로직을 짜지 말고 TemporalAdjusters를 쓴다 — dt.with(TemporalAdjusters.next(DayOfWeek.FRIDAY)), dt.with(TemporalAdjusters.lastInMonth(DayOfWeek.SUNDAY)).

문자열 파싱과 포맷팅

  • 포맷팅(객체→문자열): DateTimeFormatter.ofPattern("yyyy년 MM월 dd일")로 패턴을 만들고 date.format(formatter).
  • 파싱(문자열→객체): LocalDate.parse(text, formatter) — 입력 문자열의 실제 형식과 패턴이 정확히 일치해야 한다.
  • 패턴 문자는 대소문자를 철저히 구분한다 — MM은 월, mm은 분(전혀 다른 의미!). HH는 24시간제, hh는 12시간제(a로 오전/오후 표시).

정리

  • 날짜/시간 계산은 직접 하면 거의 확실히 버그가 생긴다 — java.time 패키지를 쓰는 게 기본.
  • 국내 서비스라면 LocalDateTime이 기본 선택, 국제화가 필요하면 ZonedDateTime, UTC 기준 절대 시각이 필요하면 Instant.
  • "특정 시점"은 Temporal/TemporalAccessor 계열, "시간의 양"은 TemporalAmount(Period/Duration) 계열로 나뉜다.
  • 모든 날짜/시간 클래스는 불변 — 변경 메서드는 항상 새 객체를 반환하므로 반환값을 받아써야 한다.
  • 복잡한 날짜 계산은 TemporalAdjusters 같은 이미 구현된 도구를 활용하고, 문자열 변환은 DateTimeFormatter의 패턴 대소문자를 정확히 맞춘다.
